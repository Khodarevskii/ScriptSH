# Почему архив не поднимался и что исправлено

## Коротко

Секреты Keycloak читались через `docker exec -it`. Флаг `-t` выделяет
псевдотерминал, tty-дисциплина заменяет `\n` на `\r\n`, и в переменную попадает
хвостовой `\r`. Дальше это значение идёт в `sed` как шаблон поиска — а в
`visiology-realm.json` символа `\r` нет, поэтому **подмена секретов на болванки
молча не срабатывала**. `sed` при этом возвращает 0, ошибки в логе нет.

Следствие: в архив уезжал realm с секретами **исходного** стенда. При
восстановлении `restore.sh` искал болванки, не находил их, ничего не подставлял —
и импортировал realm с чужими секретами. Клиенты Keycloak получали
`invalid_client_credentials`, дашборды падали с DAX-ошибкой.

Именно это в проектных заметках было записано как «известная проблема
рассинхрона m2m-секрета, лечится руками через kcadm». Это не особенность
Visiology, а дефект скриптов.

## Почему дефект не был заметен

1. `sed` не считает «ничего не найдено» ошибкой — код возврата 0.
2. Обе стороны (backup и restore) ломаются согласованно: раз болванка не попала
   в JSON, то и на restore подставлять нечего, «лишнего» `\r` в JSON тоже не
   появляется. Файл остаётся валидным, импорт проходит, всё выглядит успешным.
3. При восстановлении **на тот же стенд** секреты исходного и целевого стендов
   совпадают, и round-trip работает. Ломается только перенос на другой стенд или
   восстановление после переустановки.

Проверено воспроизведением механизма (три сценария: как было, опасный
промежуточный, после починки).

## Опасность частичной починки — важно

Если починить **только backup**, болванки начнут корректно попадать в архив, и
тогда впервые заработает ветка подстановки в `restore.sh`:

```bash
sed -i "s/${m2m_secret_old}/${m2m_secret}/g" ${MAIN_BACKUP_DIR}/visiology-realm.json
```

Здесь заражённое значение стоит **справа**, то есть `\r` вставляется внутрь
JSON-строки. Такой файл `kc.sh import` не примет (Jackson валится на unquoted
control char, code 13), а `restore.sh` глушит ошибку импорта через `|| true` —
при том что realm к этому моменту **уже удалён** строкой
`kcadm.sh delete -x realms/<realm>`. Итог был бы хуже нынешнего: realm потерян
целиком.

Поэтому чинить нужно **обе стороны**. Для этого есть `patch-restore-keycloak.sh`.

## Что исправлено в `visiology-backup.sh`

| Что | Было | Стало |
|---|---|---|
| Чтение секретов Keycloak | `docker exec -it` | `docker exec -i` + `tr -d '\r\n'` |
| Подмена секретов | `sed` без проверок | проверка наличия значения ДО, проверка результата ПОСЛЕ, аварийный останов |
| Экспорт realm | ошибка глушилась, в архив мог уехать старый файл из контейнера | старый файл удаляется, проверяется `test -s` и наличие `"realm"` |
| Контроль архива | нет | секретов стенда в realm-json не остаётся, `\r` в файле нет |
| Файлы секретов (dm/ai/onec) | `>>` (повторный прогон склеивал два ключа) | `>` + проверка на непустоту, байты сохраняются как есть |
| Поиск контейнеров | `docker ps \| grep \| awk` (ловит колонку IMAGE, при нескольких совпадениях склеивает ID) | `docker ps --filter name=` + `head -1`, отсутствие контейнера — ошибка |
| Выгрузка ClickHouse | «хотя бы одна таблица» | падает, если выгружено не всё; при ошибке данных удаляется и `.sql` (иначе таблица считалась выгруженной без данных) |
| Пайплайны | ошибки в середине конвейера терялись | `set -o pipefail` |
| Новое | — | `keycloak-clients.map` в архиве: соответствие «docker secret → clientId» |

Байты файлов секретов (`dm-secret.txt` и др.) намеренно **не** нормализуются:
`restore.sh` отдаёт их в `docker secret create`, и Fernet-ключи должны
восстановиться ровно тем же набором байт.

Флаг `--ignore-keycloak-secret-mismatch` оставлен на случай, когда секрет клиента
в Keycloak реально разошёлся с docker secret и бэкап останавливать нельзя. Архив
тогда помечается файлом `KEYCLOAK-SECRETS-NOT-NORMALIZED.txt`.

## Порядок применения

```bash
# 1. Обновить свой скрипт
sudo cp visiology-backup.sh /var/lib/visiology/scripts/v3/
sudo chmod +x /var/lib/visiology/scripts/v3/visiology-backup.sh

# 2. Закрыть зеркальный дефект в штатных скриптах (делает .bak, идемпотентно)
sudo cp patch-restore-keycloak.sh visiology-keycloak-sync.sh /var/lib/visiology/scripts/v3/
sudo chmod +x /var/lib/visiology/scripts/v3/*.sh
cd /var/lib/visiology/scripts/v3/
sudo ./patch-restore-keycloak.sh
sudo grep -n 'cat /run/secrets/KEYCLOAK' restore.sh backup.sh

# 3. Снять новый бэкап
sudo ./visiology-backup.sh 2>&1 | tee ~/backup-run.log

# 4. Проверить архив ДО восстановления
ARCH=$(ls -t *-backup-v*-*.tar.gz | head -1)
mkdir -p /tmp/chk && tar -xzf "$ARCH" -C /tmp/chk backup/visiology-realm.json backup/keycloak-clients.map
grep -c -E '68c96230|749e9d46|49d410ba|23e5da38' /tmp/chk/backup/visiology-realm.json   # должно быть 4
LC_ALL=C grep -c $'\r' /tmp/chk/backup/visiology-realm.json                             # должно быть 0
cat /tmp/chk/backup/keycloak-clients.map

# 5. Восстановление и контроль
sudo ./restore.sh --archive-name "$ARCH" --with-clickhouse true --with-keycloak true 2>&1 | tee ~/restore-run.log
sudo ./visiology-keycloak-sync.sh --check     # сверка без изменений
sudo ./visiology-keycloak-sync.sh             # синхронизация, если есть расхождения
```

Шаг 4 — главный: если там не 4 болванки, архив восстанавливать бессмысленно,
причину видно сразу.

## `visiology-keycloak-sync.sh`

Автоматизирует ручную процедуру kcadm из инструкции по восстановлению и
распространяет её на все четыре клиента, а не только `visiology_m2m`. Работает по
карте `keycloak-clients.map` из архива, идемпотентен, значения секретов не
печатает. Режим `--check` только сверяет. Отдельно проверяет, что realm вообще
существует — если импорт не прошёл, это видно сразу.

После полной починки обеих сторон этот скрипт нужен уже как контроль, а не как
обязательный шаг лечения.

## Многонодовый ClickHouse

Документация 3.17 («Ускорение загрузки данных») описывает горизонтальное
масштабирование CH: параметр `CLICKHOUSE_COUNT` в `defaults.env`, отдельный
`visiology3-ch-<N>.yml` на каждую ноду, метки нод Swarm `v3-clickhouse-<N>`,
свой `SERVER_ID`. Отсюда и берётся метка `clickhouse-1` в раскладке архива —
это номер ноды, а не произвольная строка.

Прежняя версия скрипта была жёстко привязана к одной ноде: один том
`visiology3_clickhouse_data`, одна метка, один снапшот. На установке с
несколькими нодами она забрала бы только первый шард, а архив выглядел бы
успешным. На стенде с одной нодой это никогда бы не всплыло.

Что сделано:

- **Ноды определяются автоматически, а не задаются константой.**
  `detect_ch_nodes` берёт список хостов CH из переменной `CLICKHOUSE_HOSTS`
  самого backup-service — того же источника, по которому штатный код при
  восстановлении ищет каталоги, — а имя тома из спецификации сервиса Swarm по
  точке монтирования `/var/lib/clickhouse`. Резервный путь (перечисление
  сервисов) остаётся на случай, если backup-service недоступен. Имя тома
  больше не хардкод: при переименовании скрипт это увидит, а не соберёт
  пустой дамп.
- **Один снапшот на все локальные ноды.** Срез получается одномоментным сразу
  для всех шардов, что для распределённых данных важнее, чем для одной ноды.
  Копия каждой ноды удаляется сразу после её выгрузки, чтобы не требовать
  суммарного объёма по всем нодам одновременно.
- **Выгрузка в `clickhouse/<хост>/{sql,data}`** по фактическому имени хоста из
  `CLICKHOUSE_HOSTS`.
- **Ноды на других хостах — аварийный останов.** LVM-снапшот снимается с
  локального корня и чужие хосты не видит физически. Скрипт сообщает, какие
  ноды и на каком хосте пропущены, и прерывается: неполный архив, выглядящий
  успешным, — ровно то, от чего лечим.
- **Сверка с `CLICKHOUSE_COUNT`:** если найденное число сервисов не совпадает с
  объявленным в `defaults.env`, выводится предупреждение.
- Новые флаги: `--ch-node ИМЯ` (выгрузить одну ноду по имени хоста),
  `--ch-only` (только CH, без
  postgres/keycloak/minio и без упаковки — режим для дополнительных хостов),
  `--allow-partial-clickhouse` (осознанно собрать неполный архив, помечается
  файлом `CLICKHOUSE-PARTIAL.txt`).

Порядок для нескольких хостов: на каждом дополнительном хосте
`./visiology-backup.sh --ch-only --ch-node <имя>`, затем перенести полученные
`backup/clickhouse/<имя>` на основной хост и упаковать вместе с остальным
бэкапом.

При одной ноде поведение не меняется: определение даёт ровно тот же
`clickhouse-1` и тот же том, что были заданы константами (проверено на моках
для одной и двух нод).

Отдельно стоит посмотреть штатную утилиту
`/var/lib/visiology/scripts/v3/utils/store_secrets.sh -f <file>` — она
упоминается в документации как способ выгрузить сгенерированные пароли одним
файлом. Возможно, часть работы с `/run/secrets` можно переложить на неё.

## Сверка с эталонным штатным архивом

Разобран реальный штатный архив `backup-v3.13-2025-10-01-12-26-50.tar.gz`.

Что **совпало** с тем, что собирает наш скрипт:

- каталоги `backup/clickhouse/clickhouse-1/sql/` и `.../data/` — путь и метка ноды верны;
- файлы данных **без расширения**, имя файла = имя таблицы;
- схемы — `<таблица>.sql`;
- `postgres/`, `smartforms/`, `secrets/` — по одному файлу;
- minio хранится своей объектной раскладкой: каждый объект — каталог
  `minio/dev/<имя>.xlsx/` с частями и `xl.meta` внутри (в архиве 2204 файла
  `.meta`). Наш `docker cp` копирует ровно это, отличий нет.

Что **разошлось** и было исправлено:

| | эталон | было у нас |
|---|---|---|
| файлов в `sql/` | 7232 | по числу таблиц |
| файлов в `data/` | **7210** | по числу таблиц |

Разница ровно 22. Первоначально я объяснил её представлениями и словарями и
сделал для них выгрузку только схемы. **Это оказалось неверно** — исходный код
backup-service показал другое.

## Разбор кода backup-service

Сервис — `python3 /main.py`, тонкий HTTP-обработчик; логика в `/Backuper.py`,
пути в `/Config.py`. Каталог `${BACKUP_DIR}/backup` смонтирован в контейнер как
`/mnt/volume` (`backup-service.yml:43`).

**`clickhouse-1` — это имя хоста, а не номер ноды.**

```python
# Config.py
CLICKHOUSE_HOSTS = os.getenv('CLICKHOUSE_HOSTS', '').split()
# Backuper.py
for connection in self.config.connection:
    host = connection.host
    backup_dir = join(self.config.backup_dir, host)
```

Имя каталога в архиве буквально равно элементу `CLICKHOUSE_HOSTS`. Скрипт
теперь берёт этот список у самого backup-service — то есть из того же источника,
которым при восстановлении пользуется штатный код, — а имя тома по-прежнему из
спецификации сервиса Swarm. Ни одного угаданного значения не осталось.

**Откуда берутся 22.** В `_backup` перенаправление создаёт файл ещё до запуска
команды, поэтому `.sql` появляется для каждой таблицы из списка независимо от
результата. А дальше:

```python
if exit_code != 0:
    logger.warning(f'The table: {table} disappeared suddenly')
    continue          # <- файла данных для этой таблицы не будет
```

То есть 22 объекта — это таблицы, **исчезнувшие между `SHOW TABLES` и
`SHOW CREATE TABLE`**, а не представления. Штатный дамп снимается с живой базы,
и такая гонка для него штатна: в эталонном архиве лежат 22 пустых `.sql` без
данных.

Для представлений и словарей штатный код исключений не делает: `SHOW CREATE` для
них проходит, `SELECT *` тоже, оба файла создаются. Поэтому **правка откачена** —
данные снова выгружаются для всех объектов, как в штатном дампе.

**Наш случай при этом строже, и это преимущество.** Мы выгружаем с замороженной
копии LVM-снапшота: таблицы исчезать не могут. Любое расхождение — реальная
ошибка, а не гонка, поэтому проверка полноты требует `sql == data == total` и
прерывает сборку. Побочный вывод: эталонный штатный архив молча потерял данные
22 таблиц, а наш метод эту дыру закрывает.

В лог выводится `sql N, data M, ожидалось по N` — сравнимо с эталоном напрямую.
Наши числа должны быть равны между собой, а не отличаться на 22.

## Что ещё видно из кода restore

- `DROP DATABASE` + `CREATE DATABASE` перед восстановлением — база сносится
  целиком, содержимое архива становится единственным источником.
- Схемы накатываются перебором `glob('sql/*')`, данные — перебором
  `glob('data/*')`. Порядок произвольный, никакого манифеста нет.
- **Пустые файлы данных пропускаются** (`if not os.path.getsize(data): continue`),
  так что нулевой файл безопасен.
- `.sql` исполняется как есть: `clickhouse-client < файл`. Никакой обработки —
  ни снятия `UUID`, ни подмены `CREATE` на `ATTACH`. Значит вопрос про содержимое
  `.sql` закрыт: наш сырой `SHOW CREATE TABLE` подходит.
- Имя таблицы восстанавливается как `data.split(os.path.sep)[-1]`, а для схем —
  `table.split(os.path.sep)[-1].split('.')[0]`, то есть **по первой точке**.
  Таблица с точкой в имени восстановится под усечённым именем. Скрипт теперь
  предупреждает, если такие имена есть.

Оговорка: эталонный архив снят на версии **3.13**, платформа сейчас 3.16.1.
Код backup-service прочитан на 3.16.1, и раскладка совпадает.

## Что осталось проверить (вне этой правки)

- **Формат дампа ClickHouse.** Совпадение `backup/clickhouse/clickhouse-1/{sql,data}`
  со штатным по-прежнему проверено только опытным путём. Скрипт теперь сообщает,
  если в базе есть `View`/`MaterializedView`/`Dictionary`: они выгружаются как
  обычные таблицы, и `INSERT` в них при восстановлении может не пройти. Стоит
  сверить список с содержимым штатного архива.
- **Дубль источника правды по Keycloak.** Если БД Keycloak входит в дамп
  `postgres`, то после восстановления секреты приходят из БД, а не из
  realm-json — тогда `--with-keycloak` вообще ни на что не влияет.
  Проверяется одной командой на стенде: посмотреть список БД, которые снимает
  backup-service.
- **Файл `restore.sh` в этом репозитории** — это склейка вывода двух `cat`
  (строки 1–321 — штатный `backup.sh`, строка 321 содержит приглашение
  терминала, строки 322+ — собственно `restore.sh`). Как скрипт он не запустится;
  для разбора этого достаточно, но патч применяйте к файлу на стенде.

## Ограничение

Ни один из скриптов здесь не запускался против живого стенда — в этой среде нет
ни Docker, ни Visiology. Проверено: синтаксис (`bash -n`) всех трёх файлов,
работа `patch-restore-keycloak.sh` на реальных строках `restore.sh` (4 строки,
идемпотентность, откат при ошибке), экранирование `sed` на спецсимволах и
воспроизведение самого механизма поломки на моделях без Docker.
