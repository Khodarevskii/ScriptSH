## КЛЮЧЕВАЯ ИСТОРИЯ ПРОБЛЕМЫ COW (важно понять, чтобы не повторять)
Пробовали 3 модели среза ClickHouse:
1. **overlay** (снапшот ro + запись сверху) — COW переполнялся от copy-up parts.
2. **rw-снапшот** (CH прямо на снапшоте) — COW переполнялся. РАЗОБРАЛИСЬ ПОЧЕМУ:
   - Заглушили лог-таблицы CH (text_log 2.46G, metric_log 1.34G и пр.) конфигом
     zz-backup-quiet.xml (remove="1") — НЕ помогло полностью.
   - Поставили noatime,nodiratime на монтирование — НЕ помогло.
   - Метрики CH показали: CH пишет всего **68 КБ** (OSWriteBytes), а COW рос на
     ГИГАБАЙТЫ. Вывод: **COW растёт НЕ от нашего CH, а от записи БОЕВОЙ системы
     в корень.** LVM-снапшот COW сохраняет старые блоки при записи в origin
     (живой корень: боевой CH, postgres, k8s, логи). Пока снапшот жив долго
     (десятки минут выгрузки), боевые записи в корень переполняют COW.
3. **КОПИЯ** (ТЕКУЩАЯ, рабочая) — снапшот ro → cp данных CH в отдельную папку →
   снапшот СРАЗУ удаляется → CH на копии → выгрузка с копии. Снапшот живёт только
   на время cp → COW не успевает переполниться. Проверена ранее полным циклом.

**Идею "снапшотить только том CH, а не корень" (изоляция) — ОТВЕРГЛИ:** данные CH
на общем корне (`/dev/mapper/ubuntu--vg-ubuntu--lv`, `/`), вынос на отдельный том =
инвазивно, лезем в логику Visiology, риск при обновлениях. НЕ делаем.

## РАСЧЁТ ДЛЯ БОЕВОЙ (важно)
- Стенд: CH ~15-16G, копия ~2.5 мин, COW диск sdg 50G. Снапшот живёт минуты — ок.
- Боевая: CH ~400G, копирование ~40-70 мин (снапшот живёт ~час), НО под снапшот
  выделено **600G** COW. За час боевых записей COW наберёт ~10-17% (боевая пишет
  десятки ГБ/час) — с запасом. Копия на боевой сработает благодаря большому COW.
- COW в скрипте вычисляется автоматически = всё свободное на SNAP_PV
  (стенд 50G, боевая 600G). Самонастройка.
- Штатный полный бэкап боевой = 14G (данные CH отлично жмутся). Наш архив будет
  примерно столько же — мы используем ТОТ ЖЕ механизм (SELECT Native), что штатный.

## АРХИТЕКТУРА ФИНАЛЬНОГО СКРИПТА (visiology-backup.sh)
Свой оркестратор на базе штатного backup.sh, ОДИН проход без перепаковки. Кладётся
В ТУ ЖЕ ПАПКУ `/var/lib/visiology/scripts/v3/` (нужны config.env/defaults.env +
относительные пути extended-services/env-files/custom-configs). Собирает всё в
папку backup/ и пакует один раз. Этапы:
1. backup-service БЕЗ clickhouse (только postgres, smartforms) — тот же HTTP-вызов
   что штатный, но databases:["postgres","smartforms"].
2. custom scripts (dashboard-viewer), extended-services, env-files, custom-configs — cp -ra.
3. keycloak — kc.sh export + sed-подмена 4 секретов на болванки (ОДИН-В-ОДИН как штатный).
4. minio (docker cp dev/permanent), секреты.
5. ClickHouse — НАША логика (модель копии, см. выше) → Native-выгрузка параллельно
   (xargs -P4) в backup/clickhouse/clickhouse-1/{sql,data}/.
6. tar один раз → архив в папке Visiology.

Особенности:
- Секреты: тянем dm (DATA_MANAGEMENT_SECRET_KEY) + ai + onec, КАЖДЫЙ условно по
  наличию контейнера (на стенде снимется только dm). mail НЕ тянем.
- keycloak ВХОДИТ в бэкап. При restore m2m-секрет рассинхронизируется — нужна ручная
  синхронизация (kcadm). Это отдельная известная проблема (см. ниже).
- Дебаг-режим: флаг `-d`/`--debug` (set -x). Версия: VERSION="${VI_VERSION:-3.16.1}".
- Ротацию предыдущих архивов УБРАЛИ (история хранится). Убирается только промежуточный
  мусор текущего прогона.
- Финальную полную проверку архива УБРАЛИ (долгий проход, не гарантирует рабочесть).
- Глушащий конфиг zz-backup-quiet.xml оставлен (чтобы CH на копии не раздувал логами).
- COW = всё свободное место на SNAP_PV (авторасчёт через pvs).

## KEYCLOAK m2m (известная проблема при restore)
После restore keycloak-realm восстановлен, но штатный restore рассинхронизирует
m2m-секрет → invalid_client_credentials → дашборды не грузят данные (DAX-ошибка).
РЕШЕНИЕ (работает): синхронизировать секрет клиента visiology_m2m в keycloak с
docker secret KEYCLOAK_M2M_SECRET через kcadm внутри контейнера keycloak:
```
docker exec -it <keycloak> bash
/opt/keycloak/bin/kcadm.sh config credentials --server http://localhost:8080/v3/keycloak --realm master --user $(cat /run/secrets/KEYCLOAK_ADMIN) --password $(cat /run/secrets/KEYCLOAK_ADMIN_PASSWORD)
M2M=$(cat /run/secrets/KEYCLOAK_M2M_SECRET)
CID=$(/opt/keycloak/bin/kcadm.sh get clients -r Visiology -q clientId=visiology_m2m --fields id --format csv --noquotes)
/opt/keycloak/bin/kcadm.sh update clients/$CID -r Visiology -s secret="$M2M"
```

## КОМАНДЫ ЗАПУСКА/ОЧИСТКИ (актуальные)
Запуск:
```
sudo cp visiology-backup.sh /var/lib/visiology/scripts/v3/
sudo chmod +x /var/lib/visiology/scripts/v3/visiology-backup.sh
cd /var/lib/visiology/scripts/v3/
sudo ./visiology-backup.sh 2>&1 | tee ~/backup-run.log
```
Очистка остатков (если прерван / после kill -9 trap не срабатывает):
```
sudo pkill -9 -f visiology-backup.sh
sudo docker rm -f ch_temp_backup 2>/dev/null
sudo fuser -km /mnt/vis_snap 2>/dev/null
sudo umount -l /mnt/vis_snap 2>/dev/null
sudo lvremove -y ubuntu-vg/visiology_backup_snap 2>/dev/null
sudo rm -rf /tmp/vis_ch_conf /mnt/disk2/vis_ch_copy
sudo lvs
```
Проверка что все части в архиве:
```
ARCH=$(ls -t /var/lib/visiology/scripts/v3/*-backup-v*-*.tar.gz | head -1)
pigz -dc "$ARCH" | tar -t | grep -E 'clickhouse/clickhouse-1/(sql|data)/|postgres|minio|visiology-realm|secrets/|command.txt' | sort -u | head
```
