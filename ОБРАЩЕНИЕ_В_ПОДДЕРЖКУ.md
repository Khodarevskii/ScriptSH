# Обращение в техническую поддержку Visiology

**Тема:** восстановление из резервной копии завершается ошибкой HTTP 500, при этом `restore.sh` сообщает об успехе

**Версия платформы:** 3.16.1 (воспроизводится и на 3.13)
**Развёртывание:** Docker Swarm, один узел, `PROJECT=visiology3`
**Компонент:** `visiology3_backup-service`, штатные `backup.sh` и `restore.sh` из `/var/lib/visiology/scripts/v3/`

---

## 1. Краткая суть

При восстановлении из резервной копии `backup-service` возвращает `HTTP 500`, хотя `pg_restore` фактически доходит до конца. Штатный `restore.sh` этот код ответа не проверяет и в любом случае печатает `Restore completed successfully!`.

Ниже описаны пять независимых дефектов, обнаруженных при разборе. Первые два приводят к **молчаливой потере данных** — это основная причина обращения.

---

## 2. Дефект 1. `restore.sh` не проверяет результат восстановления баз

**Где:** `/var/lib/visiology/scripts/v3/restore.sh`

```bash
docker exec "${container_id}" curl -sLv --request POST --url http://127.0.0.1:8000 \
  --header 'Content-Type: application/json' \
  --data '{"command":"restore","databases":'"${databases_str}"'}'
```

У `curl` не задан ключ `-f`. Без него код возврата равен нулю при любом ответе сервера, включая `HTTP 500`. Скрипт продолжает работу и завершается сообщением:

```
Restore completed successfully!
```

**Последствие.** Администратор видит сообщение об успехе при полностью или частично невосстановленной базе. Обнаружить это можно только вручную, вчитавшись в подробный вывод `curl`.

Тот же ключ отсутствует в `backup.sh` при вызове `command=backup`, то есть неудачное **создание** резервной копии тоже проходит незамеченным, и в архив попадает каталог без дампов баз.

**Просьба:** проверять код ответа `backup-service` и прерывать выполнение при ошибке.

---

## 3. Дефект 2. `backup-service` отдаёт 500 на неустранимые и на несущественные ошибки одинаково

**Наблюдение.** Ответ сервиса при восстановлении:

```
< HTTP/1.0 500 Internal Server Error
< Server: SimpleHTTP/0.6 Python/3.13.2

(1, ['pg_restore: error: COPY failed for table "jobparameter": ERROR:  insert or update on table "jobparameter" violates foreign key constraint "jobparameter_jobid_fkey"',
     'DETAIL:  Key (jobid)=(675565) is not present in table "job".',
     'pg_restore: error: COPY failed for table "state": ERROR:  insert or update on table "state" violates foreign key constraint "state_jobid_fkey"',
     'DETAIL:  Key (jobid)=(675572) is not present in table "job".',
     'pg_restore: warning: errors ignored on restore: 2'])
```

Последняя строка — `errors ignored on restore: 2` — означает, что `pg_restore` **завершился**, пропустив две строки. Восстановление состоялось.

Тем не менее сервис возвращает `500`, не разделяя случаи «восстановление не выполнено» и «выполнено, пропущено N строк». Вызывающая сторона отличить их не может.

**Просьба:** различать фатальный сбой и завершение с пропусками. Например, возвращать `200` с перечнем предупреждений, а `500` — только когда `pg_restore` завершился ненулевым кодом.

## 4. Дефект 3. Нарушение ссылочной целостности в таблицах Hangfire

**Наблюдение.** Ошибки возникают на таблицах планировщика Hangfire: `job`, `jobparameter`, `state`. Строка `jobparameter` ссылается на задание `jobid=675565`, отсутствующее в восстановленной таблице `job`.

**Условия.** Резервная копия снималась на работающей платформе — то есть штатным образом, как предписывает документация. Hangfire в это время непрерывно создаёт и удаляет задания.

**Вопросы к разработке:**

1. Снимается ли дамп PostgreSQL в единой транзакции (согласованный срез)? Если да, нарушения ссылочной целостности внутри дампа быть не должно, и причину следует искать на стороне восстановления.
2. Восстанавливаются ли данные в схему с уже созданными ограничениями внешнего ключа? Если да, порядок загрузки таблиц становится значимым, и требуется `--disable-triggers` либо отложенная проверка ограничений.
3. Используется ли параллельное восстановление (`pg_restore -j`)? При включённых ограничениях оно нарушает порядок загрузки.

**Просьба:** исключить таблицы очереди заданий Hangfire из резервной копии либо восстанавливать их с отключённой проверкой ограничений. Содержимое очереди фоновых заданий не подлежит переносу: платформа создаёт её заново.

## 5. Дефект 4. Восстановление на работающей платформе повреждает данные

**Наблюдение.** При восстановлении без остановки сервисов дополнительно возникают:

- `UNKNOWN_TABLE` в ClickHouse — `data-management-service` обращается к таблицам, пока идёт `DROP DATABASE` / `CREATE DATABASE`;
- ошибки нарушения уникальности в Smart Forms — сервис пишет в те же таблицы, в которые идёт восстановление.

**Существенно:** воспроизводится на архиве, собранном **штатным** `backup.sh`, то есть не связано со сторонними средствами.

При остановленных сервисах (`docker service scale ...=0` для `data-management-service`, `dashboard-service`, `workspace-service`, `smart-forms`, `formula-engine`, `python-script-service`, `dashboard-viewer`) то же восстановление проходит без единой ошибки.

**Просьба:**

1. Зафиксировать в документации требование останавливать сервисы перед восстановлением, с указанием конкретного перечня;
2. либо реализовать остановку и запуск в самом `restore.sh`, как это уже сделано для `data-management-service` при восстановлении секрета `DATA_MANAGEMENT_SECRET_KEY`.

## 6. Дефект 5. Штатный `backup.sh` молча теряет данные части таблиц ClickHouse

**Где:** `/Backuper.py` внутри контейнера `backup-service`.

```python
if exit_code != 0:
    logger.warning(f'The table: {table} disappeared suddenly')
    continue          # файл данных для этой таблицы не создаётся
```

Файл `sql/<таблица>.sql` создаётся перенаправлением вывода **до** запуска команды, поэтому появляется всегда, независимо от результата. При неуспешном `SHOW CREATE TABLE` оператор `continue` пропускает выгрузку данных.

**Наблюдение на реальном архиве** (эталонный архив, снятый штатными средствами): 7232 файла в `sql/` и 7210 файлов в `data/`. Разница в 22 объекта — таблицы, исчезнувшие между `SHOW TABLES` и `SHOW CREATE TABLE`. В архиве им соответствуют пустые `.sql` без данных.

**Последствие.** Ни `backup.sh`, ни `restore.sh` о расхождении не сообщают: при восстановлении пустые файлы данных пропускаются штатным кодом без предупреждения. Потеря обнаруживается только сравнением количества файлов вручную.

**Просьба:** сверять количество выгруженных схем и файлов данных и сообщать о расхождении в результате операции.

## 7. Дефект 6. Чтение секретов Keycloak через псевдотерминал

**Где:** `backup.sh` и `restore.sh`, ветка `--with-keycloak true`.

```bash
m2m_secret=$(docker exec -it "${keycloak_container_id}" cat /run/secrets/KEYCLOAK_M2M_SECRET)
```

Ключ `-t` выделяет псевдотерминал, дисциплина которого заменяет `\n` на `\r\n`. Подстановка команд срезает завершающий `\n`, и в переменной остаётся символ `\r`.

**Последствия.**

В `backup.sh` значение идёт в левую часть `sed` — подстановка не находит совпадения. Команда `sed` при этом возвращает нулевой код, ошибки нет, и в архив попадают **действующие секреты исходного стенда** вместо заглушек.

В `restore.sh` то же значение идёт в правую часть `sed`, то есть символ `\r` вставляется **внутрь строки** JSON-файла realm. Такой файл `kc.sh import` не принимает. Ошибка импорта заглушена через `|| true`, а realm к этому моменту уже удалён командой `kcadm.sh delete -x realms/<realm>` — realm теряется целиком.

**Просьба:** использовать `docker exec -i` без `-t` и отбрасывать управляющие символы, а результат импорта realm проверять до удаления существующего.

---

## 8. Как воспроизвести

1. Снять резервную копию штатным `backup.sh` на работающей платформе.
2. Восстановить её штатным `restore.sh --archive-name <архив>`, не останавливая сервисы.
3. В подробном выводе `curl` наблюдать `HTTP/1.0 500 Internal Server Error` и текст ошибок `pg_restore`.
4. Убедиться, что скрипт при этом завершается сообщением `Restore completed successfully!` с нулевым кодом возврата.
